# Friendly Camp

وب‌اپلیکیشن فارسی رزرو و مدیریت تورهای طبیعت‌گردی با React، Vite، TypeScript و Express.

## اجرای کامل با Docker Desktop روی لوکال

Docker Desktop را با موتور Linux containers اجرا کنید. در پوشه پروژه:

```powershell
node scripts/prepare-docker-local.mjs
docker compose up -d --build --wait
```

سایت: `http://localhost:3001` · مدیریت: `http://localhost:3001/admin`

رابط ساخته‌شده React و API در یک کانتینر با Node.js اجرا می‌شوند؛ SQLite داخل Node است و سرویس پایگاه داده جدا نیاز ندارد. پورت فقط روی خود کامپیوتر باز می‌شود. اجرای محلی قبلی روی پورت ۳۰۰۱ را پیش از راه‌اندازی کانتینر متوقف کنید.

پوشه‌های `data` و `public/uploads` مستقیماً از پروژه به کانتینر متصل هستند و پس از restart، rebuild یا `docker compose down` باقی می‌مانند. هم‌زمان نسخه خارج از داکر را روی همین داده‌ها اجرا نکنید. تنظیمات اختیاری `.env` و سپس `.env.local` خوانده می‌شوند؛ کلید خصوصی نشست در `.docker/local.env` نگهداری و از Git و تصویر داکر مستثنا می‌شود. حساب‌های فعلی حفظ می‌شوند؛ برای ساخت مدیر تازه از متغیرهای `ADMIN_BOOTSTRAP_*` مطابق راهنمای مدیریت استفاده کنید. در Compose محلی، پرداخت روی sandbox تنظیم شده است.

```powershell
docker compose ps
docker compose logs --tail=50 app
docker compose restart app
docker compose down
```

پس از تغییر کد، `docker compose up -d --build --wait` را دوباره اجرا کنید. تنظیمات Compose این بخش مخصوص اجرای لوکال است.

در اتصال پوشه ویندوز، `BOOKING_FILE_PERMISSIONS=host` اجازه می‌دهد ACL خود میزبان دسترسی فایل SQLite را تعیین کند؛ کانتینر همچنان با کاربر غیرریشه اجرا می‌شود. خارج از این تنظیم صریح، سطح دسترسی SQLite به صورت پیش‌فرض `0600` اعمال می‌شود. بررسی سلامت کانتینر، هم پاسخ سرور و هم API تورها و اتصال SQLite را کنترل می‌کند.

## اجرای توسعه

برای اجرای رایگان روی همان سرویس Render با PostgreSQL و فایل‌های خصوصی Supabase، [راهنمای استقرار](RENDER_SUPABASE_DEPLOYMENT.md) و `render.yaml` آماده‌اند. شناسه سرویس و پروژه مقصد در `deployment/render-target.json` ثبت شده است. نسخه لوکال Docker همچنان از SQLite استفاده می‌کند؛ داده‌ها و رمزها همراه کد منتشر نمی‌شوند.

1. Node.js 22.16 یا جدیدتر را نصب کنید.
2. `npm install` را اجرا کنید.
3. `.env.example` را به `.env.local` تبدیل و secretها را تنظیم کنید.
4. با `npm run dev` برنامه را روی `http://localhost:3000` اجرا کنید.

OTP تا زمان اتصال ارائه‌دهنده پیامک عمداً پاسخ `503` می‌دهد و موفقیت جعلی نمایش نمی‌دهد.

## کنترل کیفیت

- `npm run typecheck`: بررسی TypeScript
- `npm test`: تست‌های واحد
- `npm run build`: ساخت production
- `npm run check`: اجرای تمام کنترل‌ها
- `npm audit --omit=dev`: ممیزی وابستگی‌های production

## امنیت و استقرار

در production مقدار `SESSION_SECRET` با حداقل ۳۲ کاراکتر الزامی است. TLS باید در reverse proxy فعال باشد. فایل `data/users.json` فقط persistence محلی توسعه است؛ برای استقرار چند replica باید با PostgreSQL و migration جایگزین شود. دسترسی ادمین فقط بر پایه نقش ذخیره‌شده سمت سرور انجام می‌شود و client نمی‌تواند هنگام ثبت‌نام نقش تعیین کند.

درگاه پرداخت و پیامک به credential و قرارداد سرویس‌دهنده نیاز دارند و تا اتصال آن‌ها نباید به‌عنوان عملیات موفق نمایش داده شوند.

جزئیات رزرو چهارمرحله‌ای، تنظیم رابط عمومی پرداخت و پیامک، آزمون ظرفیت هم‌زمان و نتیجه بررسی مرورگر در [گزارش اعتبارسنجی رزرو](BOOKING_VALIDATION.md) آمده است. نوبت‌های حرکت و شرایط رزرو آنلاین از بخش «رزرو آنلاین و نوبت‌های حرکت» در مدیریت تورها تعریف می‌شوند.

## خبرنامه

فرم پایین سایت با POST به `/api/newsletter/subscriptions` متصل است. ایمیل نرمال‌شده، زمان رضایت و نسخه متن حریم خصوصی در `data/newsletter.json` ذخیره می‌شوند؛ این فایل خصوصی در Git قرار نمی‌گیرد. ثبت تکراری و درخواست‌های هم‌زمان رکورد اضافه ایجاد نمی‌کنند.

در بخش مستقل «اعضای خبرنامه»، فهرست آخرین اعضا، خروجی CSV همه اعضای فعال و لغو عضویت برای مدیر و پشتیبان احراز هویت‌شده در دسترس است.

این نسخه ثبت و مدیریت عضویت را انجام می‌دهد. ارسال خودکار ایمیل و تأیید مالکیت نشانی به سرویس ارسال ایمیل متصل نشده‌اند. فایل عضویت باید روی فضای پایدار سرور نگهداری شود؛ ذخیره‌سازی فعلی برای یک فرایند سرور طراحی شده است.

## مدیریت محتوا و همکاران

نشانی `/admin` و لینک «ورود همکاران» در پاورقی به داشبورد متصل‌اند. حساب اولیه مدیر فقط از تنظیمات bootstrap موجود ایجاد می‌شود؛ رمز پیش‌فرض یا حساب عمومی مدیر وجود ندارد. مدیر از «همکاران و دسترسی‌ها» می‌تواند حساب بسازد، نقش حساب موجود را تغییر دهد یا دسترسی مدیریتی آن را با نقش «کاربر» بردارد. تغییر نقش روی نشست‌های باز نیز در درخواست بعدی اعمال می‌شود.

| نقش | دسترسی |
| --- | --- |
| مدیر | تمام بخش‌ها، انتشار محتوا، مدیریت همکاران و تاریخچه |
| نویسنده | مقصدها، نویسندگان، پیش‌نویس مقاله و متن صفحه؛ انتشار و بایگانی محتوای منتشرشده با مدیر است |
| پشتیبان | پیام‌ها و مشاوره، تأیید یا رد نظرات، اعضای خبرنامه |
| مسئول رزرو | تورها، حرکت‌ها، مبدأ و ساعت، ظرفیت، قیمت، رزروها و کد تخفیف سفر |

مقصدها، مقاله‌ها و نویسندگان، نظرات دارای رضایت انتشار، مجوزها، اطلاعات تماس، لینک حساب‌های شبکه اجتماعی و ۴۱۱ متن پایه صفحه اصلی در فرم‌های مستقل مدیریت می‌شوند. فهرست عمومی، جست‌وجو، متادیتای لینک مستقیم و نقشه سایت از محتوای منتشرشده استفاده می‌کنند. مقاله دارای تاریخ آینده تا رسیدن آن زمان نمایش داده نمی‌شود. ویرایش پیش‌نویس، نسخه قبلی منتشرشده را حفظ می‌کند؛ بایگانی یا حذف مدیر آن را از نمایش عمومی برمی‌دارد.

آب‌وهوا یک گزارش دستی مستند با دما، شرح، نشانی منبع، زمان مشاهده و پایان اعتبار است؛ اتصال خودکار به سرویس هواشناسی ایجاد نشده است. گزارش منقضی منتشر نمی‌شود. لینک مجوز باید به استعلام مشخص آن مدرک برسد؛ ورود اطلاعات در داشبورد جای تأیید مرجع صادرکننده را نمی‌گیرد.

تعریف تور و گالری، خدمات شامل/غیرشامل و برنامه روزبه‌روز از «تور و خدمات سفر» انجام می‌شود. قیمت قابل پرداخت، تاریخ، مبدأ و ساعت سوارشدن، ظرفیت و وضعیت اجرای هر حرکت از «حرکت‌ها و رزروها» می‌آیند. کد تخفیف سفر روی هزینه پایه پس از تخفیف گروهی محاسبه می‌شود؛ زمان اعتبار، تورهای مجاز، حداقل مبلغ و سقف مصرف در سرور بررسی می‌شوند. رزرو موقت مصرف کد را نگه می‌دارد و لغو رزرو پرداخت‌نشده آن را آزاد می‌کند. ظرفیت مصرف بین پردازه‌های متصل به همان SQLite اتمیک است.

محتوا، نقش‌های محول‌شده و تاریخچه آن‌ها در جدول‌های `control_records`، `staff_roles` و `control_audit` داخل `data/bookings.sqlite` نگهداری می‌شوند. این فایل و فایل‌های همراه WAL خصوصی و خارج از Git هستند و باید همراه سایر داده‌های سرور روی فضای پایدار و در نسخه پشتیبان نگهداری شوند. فرم‌های ویرایش کنترل نسخه دارند و تغییر هم‌زمان را با خطای 409 اعلام می‌کنند. تاریخچه مدیریت، تغییرات محتوایی و نقش‌ها با مقدار قبل و بعد، رویدادهای رزرو و دفتر تغییرات موجود فروشگاه را کنار هم نشان می‌دهد.

آزمون یکپارچه `tests/control.test.ts` محدودیت چهار نقش، جلوگیری از انتشار مستقیم نویسنده، تأیید نظر با رضایت، انقضای گزارش هوا، ناسازگاری نسخه، لغو فوری دسترسی نشست باز و رقابت دو پردازه برای کد یک‌بارمصرف را در محیط موقت بررسی می‌کند.

## اطلاعات ضروری پیش از فروش تور

صفحات `/terms`، `/privacy`، `/cancellation`، `/insurance`، `/legal`، `/faq` و `/support` آدرس مستقل و لینک در پاورقی دارند. متن‌های اختصاصی از «شرایط فروش و صفحات حقوقی» در داشبورد مدیریت می‌شوند. تا انتشار متن مؤثر، صفحه راهنمای عملکرد فعلی سامانه را با وضعیت روشن نمایش می‌دهد. انتشار سند برای نمایش عمومی با تأیید آن برای فروش واقعی یکسان نیست؛ مدیر باید گزینه بررسی و تأیید فروش را برای اسناد لازم ثبت کند.

در حالت پرداخت `http`، صدور پیش‌فاکتور قابل رزرو به تکمیل قوانین، حریم خصوصی، لغو، بیمه، مشخصات حقوقی برگزارکننده، نشانی و تماس، مدرک مجوز، جزئیات تور، سختی و آمادگی، وسایل، شرایط سنی و پزشکی، صلاحیت لیدر، مدرک و اعتبار بیمه، برنامه روزبه‌روز، خدمات شامل/غیرشامل، ساعت و نقطه مبدأ، بازگشت و شرایط اختصاصی لغو وابسته است. موارد کمبود در جدول حرکت‌های مدیریت نشان داده می‌شوند. پرشدن فرم‌ها جای استعلام واقعی مدرک، تأیید بیمه‌گر یا بررسی محتوای حقوقی برگزارکننده را نمی‌گیرد. مسیر sandbox همچنان آزمایشی است و وجه واقعی دریافت نمی‌کند.

رزرو واقعی به ورود حساب نیاز دارد. رزروهای متصل به حساب، پیش‌فاکتور و رسید در «رزرو و پشتیبانی» پنل شخصی نمایش داده می‌شوند. رزروهای قدیمی مهمان خودکار از روی شماره تماس یا ایمیل متصل نمی‌شوند؛ افزودن آن‌ها به حساب فقط با شماره و کد خصوصی همان رزرو انجام می‌شود و رزرو دارای مالک به حساب دیگر منتقل نمی‌شود. ستون `owner_id` با مهاجرت افزایشی به جدول رزرو موجود اضافه می‌شود.

پیش‌فاکتور و رزرو، تصویر ثابتی از اطلاعات سفر و متن و نسخه شرایط پذیرفته‌شده نگه می‌دارند. تغییر بعدی تور یا سند، شرایط ثبت‌شده رزرو قبلی را بازنویسی نمی‌کند. در صورت تعیین محدوده سن، تاریخ تولد برای بررسی سن در زمان حرکت درخواست و سمت سرور بررسی می‌شود؛ تاریخ تولد در payload رسید ذخیره نمی‌شود. چاپ یا ذخیره PDF صورت‌حساب و رسید از پنجره چاپ مرورگر انجام می‌شود؛ این سند عنوان فاکتور رسمی مالیاتی ندارد.

در `/support` درخواست، شکایت یا پیگیری استرداد با رضایت ثبت می‌شود و شماره پرونده و کد خصوصی می‌دهد. پیگیری و پیام تکمیلی با همین کد ممکن است. مدیر و پشتیبان از بخش «شکایت و پیگیری» پاسخ قابل مشاهده در پرونده می‌گذارند؛ این کار ارسال خودکار ایمیل یا پیامک نیست. پرونده‌های هنگام ورود در پنل همان حساب هم دیده می‌شوند. پرونده مهمان صرفاً با شباهت نام یا تماس در حساب دیگر نمایش داده نمی‌شود. متن پرونده‌ها و نقش‌ها در دسترس عموم نیستند؛ نشانی خصوصی دارای کد را نباید منتشر کرد.

`tests/travel.test.ts` جلوگیری از فروش ناقص، محدودیت سن، مالکیت و اتصال خصوصی رزرو، حفظ نسخه شرایط پس از تغییر، وضعیت استرداد در حساب و ثبت و پاسخ خصوصی شکایت را در دو سرور موقت بررسی می‌کند. `tests/fixtures/sales.ts` فقط برای آماده‌سازی داده‌های صریحاً آزمایشی این آزمون‌هاست و در برنامه مسیر عبور از بررسی فروش وجود ندارد.
# امکانات تکمیلی کشف سفر

- `/tours`: فیلتر مقصد، بازه تاریخ با انتخابگر شمسی، بودجه پایه هر نفر، مدت و سختی؛ انتخاب‌ها در نشانی صفحه حفظ می‌شوند. تاریخ، بودجه و ظرفیت باید هم‌زمان در یک نوبت تطبیق کنند. تقویم `/calendar` از نوبت‌ها و ظرفیت سرور استفاده می‌کند.
- `/favorites` و حساب کاربری: علاقه‌مندی مهمان در مرورگر و علاقه‌مندی عضو در SQLite و با مالکیت حساب ذخیره می‌شود؛ اطلاعات دو حساب با هم ادغام نمی‌شوند.
- `/tours/compare?ids=...`: مقایسه واقعی دو یا سه تور منتشرشده، با انتخاب مستقل نوبت و تازه‌سازی ظرفیت. قیمت ستون، هزینه پایه همان نوبت است.
- اعلان کاهش ظرفیت، **داخل حساب کاربری** است؛ ارسال پیامک/ایمیل/اعلان مرورگر ندارد. هر نوبت با رضایت کاربر و آستانه انتخابی پیگیری می‌شود؛ کاهش مشاهده‌شده تا آستانه، هر ۲۰ ثانیه بررسی و با تراکنش ثبت می‌شود. افزایش ظرفیت اعلان کاهش تولید نمی‌کند؛ پیگیری از حساب قابل توقف است. این اعلان تضمین نگهداری صندلی نیست.
- مدیریت «لیدرها و مدارک»: نام، تجربه، تصویر با رضایت، مرجع/شماره/استعلام/اعتبار مدرک ثبت و با تأیید مدیر منتشر شود. تور می‌تواند به پروفایل متصل شود. لغو انتشار یا انقضای مدرک، الزامات فروش واقعی را دوباره تحت تأثیر قرار می‌دهد. پروفایل‌ها از `/leaders` آدرس مستقل دارند؛ هیچ پروفایل نمونه‌ای به داده اصلی اضافه نشده است.
- بخش «مسیر واقعی» هر تور در مدیریت، یک فایل پیوسته GPX یا GeoJSON LineString (حداکثر ۲۰۰۰ نقطه، یک مگابایت) می‌پذیرد. مختصات به‌صورت عمومی منتشر می‌شوند. منبع GPS الزامی است. بازه‌های ارزیابی با شماره نقاط **از صفر**، مسئول/روش/زمان/انقضا و منبع مستند ثبت شوند؛ قطعات فاقد ارزیابی جاری با وضعیت نامشخص خاکستری هستند. سطح‌بندی از داده مدیریت می‌آید و خودکار یا تضمین ایمنی نیست.
- نقشه فقط پس از انتخاب کاربر بارگیری می‌شود. منبع پیش‌فرض [OpenStreetMap](https://operations.osmfoundation.org/policies/tiles/) با ذکر منبع و کش معمول مرورگر است؛ دانلود انبوه، پیش‌بارگیری یا نقشه آفلاین انجام نمی‌شود. برای میزبانی پرترافیک، ارائه‌دهنده مناسب را با `MAP_TILE_URL` (HTTPS با `{z}/{x}/{y}`)، متن و لینک مجوز تنظیم کنید. URL در مرورگر عمومی است؛ توکن محرمانه سرور در آن قرار ندهید. تغییر منبع نیاز به راه‌اندازی دوباره سرور برای CSP دارد.
- فهرست وسایل ثبت‌شده هر تور به صورت فایل متنی UTF-8 قابل دریافت است؛ فایل نمونه یا فهرست ساختگی ارائه نمی‌شود.
- داده ساختاریافته صفحات مستقل از محتوای منتشرشده ساخته می‌شود: [TouristTrip](https://schema.org/TouristTrip)، Product، Article و Person. نوع استاندارد سفر TouristTrip است. قیمت‌ها برای Schema از تومان به IRR تبدیل می‌شوند؛ تور آزمایشی یا فاقد شرایط فروش واقعی Offer نمی‌گیرد و امتیاز ساختگی درج نمی‌شود. نمایش نتیجه ویژه در موتور جست‌وجو تضمین نشده است.
